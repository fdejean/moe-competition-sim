⏺ I've now read the PDF intro, both source files, and the full server-score log.
  Here's the intuitive picture.

  The problem (from the workshop PDF)

  MoE models only activate a few "experts" per token. The router makes some
  experts hot (heavily used) and others cold. Experts are spread across devices.
  If one device holds the hot experts, it becomes the bottleneck — everyone
  else waits for it. So you periodically redeploy experts to balance load. But
  moving an expert costs bandwidth.

  Two numbers decide your score:

  - PAR (peak-to-average ratio) = busiest device load / average device load. 1.0
  = perfectly balanced. This is compute time — and it's ~97% of the score.
  - transmit = how many experts you moved. This is transfer time — only ~3% of
  the score.

  Score = how much faster your modeled runtime is than the DS-EPLB baseline. PAR
  is worth ~6000× a transmit unit, so the whole game is: get PAR down, cheaply.

  Your rebalance() function receives hotness — a history tensor of shape
  (iterations, layers, experts) telling you how loaded each expert was each
  iteration — and must return a placement (which experts sit in which device
  slots) plus which layers to actually move.

  finance_band (111.27) — the baseline everyone's stuck at

  Flo's algorithm treated it like a portfolio problem (experts = assets,
  replicas = portfolio weights):

  1. No-trade band (TAU): recompute the ideal layout every cycle, but only apply
  it to a layer if the PAR gain clears a threshold. Avoids paying transfer cost
  for trivial gains — a stable trace "deploys once, then holds."
  2. Variance-aware replication (LAMBDA): give volatile experts more copies
  (mean + λ·std), so their fluctuations get split across devices — risk
  diversification.
  3. Placement: greedy LPT (Longest-Processing-Time) on the mean load — heaviest
  expert onto the least-loaded device.

  This packs the average load near-perfectly (mean-PAR ≈ 1.05). But realized PAR
  was stuck at ~1.69. Everyone hit this same wall.

  Why the 111 wall existed — co-spiking

  Here's the key insight the whole jump rests on. Mean-balancing is solved. The
  residual PAR ≈ 1.69 doesn't come from bad average packing — it comes from
  co-spiking:

  ▎ Experts that look balanced on average can all spike in the same iteration. A
  ▎ device holding several such experts gets crushed in that moment, even 
  ▎ though their averages are fine.

  Mean-packing is blind to this — it only sees the time-average, not when the
  spikes line up. Every point from 111→114 came from teaching the placement to 
  see the spikes.

  The three real levers, intuitively:

  1. Joint-peak target (θ / "peak"): stop balancing the average. Pick the
  iterations where total load was highest (the actual co-spiking moments) and
  balance those. Critically it's the joint peak — the real peak iterations
  selected across all experts together. Peers tried per-expert percentiles (p95)
  and those failed, because a spike only hurts if experts spike at the same 
  time.
  2. Temporal block placement ("block"): instead of one load number per expert,
  give it k numbers (load in each time-block) and make sure no device is
  overloaded in any block. This makes placement time-aware — it won't stack
  experts that are busy in the same window. Only runs at EP≤128; at EP256 the
  time budget is too tight (it'd "floor" to −1e6), so it falls back to scalar.
  3. peakblock — the meta-pattern: the biggest learning. Wins come from adding 
  scenario information as extra columns the greedy balances across (temporal
  blocks, the co-spike peak, volatility), not from changing the objective. They
  proved this: swapping the L∞ "worst-block" objective for L2 (lstsq_pack 113.1)
  or dot-product (dotprod_pack 112.7) both lost. L∞ worst-block is already the
  right objective; you win by feeding it richer columns.

  Glossary of the terms you saw

  - cospike / co-spiking: experts spiking in the same iteration → the true
  source of residual PAR.
  - peak / joint-peak (θ, PEAKFRAC): balance against the busiest iterations, not
  the mean.
  - block (BLOCKS=k): split the window into k time-slices and balance across all
  of them — temporal awareness.
  - peakblock: add the joint-peak as an extra block column → placement itself
  becomes spike-aware.
  - varblock: peakblock + a volatility (std) column. Turned out neutral.
  - vblock256: the structural bet to extend block placement to EP256, the last
  unsolved regime.
  - sticky / relabel / no-trade band: the transmit levers — fewer expert moves
  at equal PAR. Tapped out around 111.8.

  What's left (the real wall now)

  At EP256 each device holds only ~2 expert slots, realized PAR is ~3.4, and the
  block-placement machinery is too slow to run inside that case's time budget —
  so it falls back to dumb scalar packing. That regime is where the remaining
  points are, and vblock256 is the current attempt to crack it.

  So the honest summary: 111→114 was three new ways of seeing co-spiking (peak
  iterations, temporal blocks, peak-as-a-column), and the discipline of adding 
  information rather than fine-tuning knobs or changing the objective.

  The packer is not the bottleneck. With perfect foresight it hits ~1.02 PAR
  even at EP256 (2 slots/device). Every point of realized PAR above ~1.05 is 
  forecasting error + redeploy lag — the cost of placing on a stale window and
  then holding that placement while load drifts. This reframes the whole
  "co-spiking" story: co-spiking is the symptom of a static placement being
  unable to track per-iteration co-fluctuation. The peakblock/block machinery
  (111→114) was attacking that indirectly — making the static placement robust
  across time-blocks and peak scenarios. It worked, but it's chipping at a gap
  whose true size is +0.97.

  Breakpoint #1 — EP scaling (the gap doubles by EP256)

  The forecasting gap grows monotonically and steeply with EP: +0.22 → +0.35 →
  +0.58 → +0.97. Reason: at high EP each device holds very few experts (EP256 ≈
  2 slots), so a single misforecast can't be averaged out across the device's
  experts. Fewer experts/device = no diversification of forecast error.
  EP128→EP256 is the cliff — and it's exactly where our block-placement turns
  off (it floors the time budget), so EP256 falls back to dumb scalar packing.

  Breakpoint #2 — the dataset that's actually failing: Mix (DS-R1)

● Here's what this repo is.

  What it is

  It's the simulator for a "MoE dynamic load-balancing" competition — a
  coding/benchmark contest (looks Codabench-hosted). MoE = Mixture-of-Experts
  LLMs. In these models each layer has many "experts," and tokens get routed
  unevenly across them, so some experts get hammered ("hot") while others idle.
  The competition challenge: write an algorithm that decides how to 
  place/replicate experts across GPUs (devices) to balance the load, scored on a
  metric called PAR (peak-to-average ratio) plus the cost of moving experts
  around between devices (redeployment transmit).

  The pieces:

  ├─────────────────────────────┼────────────────────────────────────────────┤

  │                             │ redeployment cost + a final score          │

● Here's the contract, grounded in the code. The thing you implement is one
  function — rebalance(...) — in submission.py. The simulator calls it
  periodically during the run.

  INPUT — what the simulator hands you

  def rebalance(hotness, n_device, n_red_expert):

  Arg: hotness
  Type / shape: int array (window, n_layers, n_experts)
  Meaning: A recent window of the trace — token counts per expert per layer, for

    the last collection_interval iterations (not the whole trace, not the
    future). This is your only signal about which experts are hot.
  ────────────────────────────────────────
  Arg: n_device
  Type / shape: int
  Meaning: Number of GPUs / expert-parallel ranks (the "EP" size: 32, 64, 128,
    256).
  ────────────────────────────────────────
  Arg: n_red_expert
  Type / shape: int
  Meaning: How many extra (redundant) expert slots you're allowed to add on top
    of the real experts.

  Concrete shapes:
  - DS-R1: hotness is (window, 58, 256), n_experts = 256
  - Qwen3: hotness is (window, 94, 128), n_experts = 128

  Key derived quantity — slots per device:
  n_exp_per_dev = (n_experts + n_red_expert) // n_device
  So the hardware has n_device × n_exp_per_dev physical slots, and you have
  n_red_expert more slots than there are distinct experts. That surplus is the 
  whole game: you spend it by putting the same hot expert in multiple slots so
  its tokens split across GPUs.

  OUTPUT — what you return

  A 4-tuple (change, layers_priority, deployment, _):

  Element: change
  Type / shape: bool
  Meaning: True = apply a new placement; False = keep current placement and pay
    zero transfer cost.
  ────────────────────────────────────────
  Element: layers_priority
  Type / shape: 1D int array of layer indices
  Meaning: Order to reconfigure layers in. The sim applies one layer per 
    iteration (dynamic_lb_simulator.py:154-158), so put the most-imbalanced
    layers first.
  ────────────────────────────────────────
  Element: deployment
  Type / shape: int array (n_layers, n_device, n_exp_per_dev)
  Meaning: The placement plan. Each entry is a logical expert id in [0, 
    n_experts) assigned to that (layer, device, slot). The same expert id in two

    slots = replicated across those slots/devices.
  ────────────────────────────────────────
  Element: 4th
  Type / shape: unused
  Meaning: Return None.

  The two example submissions show the extremes:
  - submissions/smoke/submission.py → returns (False, [], deployment, None) —
  never redeploys.
  - submissions/hot_expert_baseline/submission.py → returns (True, ...) and puts
  the hottest expert of each layer into the one redundant slot per device.

  How input → output is scored

  For each iteration the simulator takes the true hotness and your current
  deployment and computes (dynamic_lb_simulator.py:92-98):

  device_load[d] = Σ over slots ( expert_tokens /
  number_of_copies_of_that_expert )
  PAR            = max(device_load) / mean(device_load)      # lower is better

  Plus a transfer cost: every slot whose expert id changed costs one expert-move
  (compute_redeploy_cost), converted to seconds at 900 GB/s.

  Final score combines both:
  total_time = 60 * mean_PAR + transfer_time
  score      = 100 * baseline_time / total_time      # higher is better

  So the function's job in one sentence: given a recent window of expert load, 
  decide where to place (and how to replicate) each layer's experts so that load
  is balanced across GPUs — without redeploying so often that transfer cost 
  eats the gain. And from the EDA, the hot experts barely move over time, so the
  winning move is to redeploy rarely.

● Right instinct, mostly. Let me clear up the three things you're mixing
  together: learning, randomness, and static vs. dynamic.

  No learning, no random weights

  There is no machine learning here at all. You're not training a model, there
  are no learnable parameters, and there's nothing random to "calculate."

  The word "weight" in this codebase (e.g. weight=tokens_per_expert.sum(...) in
  the DeepSeek algorithm) does not mean a neural-net weight. It just means
  per-expert load — literally "how many tokens went to this expert." It's an
  observed count, not a learned or random number.

  What you're actually writing is a deterministic optimization / placement 
  heuristic:

  input:  observed load per expert  (a histogram)
  output: where to put each expert  (an assignment)
  goal:   make the per-GPU load as even as possible

  It's a bin-packing / load-balancing problem, the same family as "I have jobs
  of known sizes, pack them onto machines evenly." Random placement would hurt
  you — the baseline algorithms are all deterministic.

  Static vs. dynamic — the subtle part

  The API is dynamic: rebalance() gets called repeatedly during the run, and
  you're allowed to change the placement over time as load shifts. That's why
  it's called a "dynamic load-balancing" competition.

  But — and this is exactly what the EDA showed — the hot experts barely change
  over the whole trace (rank correlation 0.97–0.98 first-window vs.
  last-window). So in practice:

  ▎ A near-static strategy wins. Observe load once early, compute a good 
  ▎ placement, and then rarely or never redeploy.

  Why? The score has two terms working against each other:

  total_time = 60 · mean_PAR  +  transfer_cost
                  ↑ lower if you rebalance well     ↑ higher every time you move
  experts

  If load were volatile, you'd need to keep re-balancing (truly dynamic) and eat
  the transfer cost to keep PAR low. Since load is stable, re-balancing
  repeatedly just burns transfer cost for almost no PAR improvement. So the
  optimal policy here is close to:

  1. Watch the first window of load.
  2. Compute one good placement (replicate the hottest experts into the
  redundant slots).
  3. Return change=False forever after.

  That's why submissions/smoke/submission.py (never redeploys) is a legitimate,
  non-trivial baseline — and why the ds_eplb_sweep experiments were tuning how 
  often to redeploy rather than tuning any learned parameter.

  So, to answer directly

  - "Is this static?" — The mechanism is dynamic, but the winning strategy is
  nearly static, because the data is stable.
  - "No need to learn anything?" — Correct. Zero learning. It's deterministic
  optimization over an observed load histogram.
  - "Or calculate a random weight?" — No. The "weight" is the measured
  token-load per expert (not random, not learned), and you use it
  deterministically to decide which experts to replicate and where to place
  them.

  The only real design decisions are: how to assign/replicate experts given the 
  load (the bin-packing heuristic), and how often to redeploy (here: almost
  never).

❯ but it depend on the model?                                                   

● Good question — there are two senses of "depend on the model," and the
  distinction matters for how you write the submission.

  Your code does NOT hardcode per model

  The same rebalance() runs for every model. It adapts automatically because all
  the model-specific dimensions arrive inside the arguments:

  def rebalance(hotness, n_device, n_red_expert):
      n_layers  = hotness.shape[1]   # 58 for DS-R1, 94 for Qwen3
      n_experts = hotness.shape[2]   # 256 for DS-R1, 128 for Qwen3
      ...

  You read the shape, you don't assume it. So you write one algorithm and it
  works for both — and that's what you want, because the simulator scores you
  across the whole grid (dynamic_lb_simulator.py:341-343): models × datasets ×
  EP sizes. Hardcoding if model == "DS-R1" isn't even possible — the model name 
  is never passed to you. All you ever see is the load numbers and the
  dimensions.

  But the data differs by model, so behavior differs

  The placement you produce will differ between models because the inputs
  differ:

  ┌──────────────┬───────────────┬─────────────────────────┐
  │              │     DS-R1     │          Qwen3          │
  ├──────────────┼───────────────┼─────────────────────────┤
  │ layers       │ 58            │ 94                      │
  ├──────────────┼───────────────┼─────────────────────────┤
  │ experts      │ 256           │ 128                     │
  ├──────────────┼───────────────┼─────────────────────────┤
  │ Gini (skew)  │ ~0.27         │ ~0.41 (more imbalanced) │
  ├──────────────┼───────────────┼─────────────────────────┤
  │ EP sizes run │ 32/64/128/256 │ 32/64/128 (no 256)      │
  └──────────────┴───────────────┴─────────────────────────┘

  Qwen3's load is more skewed, so a good algorithm will naturally replicate
  experts more aggressively there — not because you wrote model-specific logic,
  but because the heuristic reacts to the higher skew it sees in hotness. Same
  code, different output, driven by the data.

  The takeaway

  - Don't write model-specific branches. You can't (no model id) and you
  shouldn't (it wouldn't generalize to the hidden datasets).
  - Do write a load-driven heuristic that scales with whatever n_layers / 
  n_experts / n_device / n_red_expert / skew it's handed.

  What does generalize across both models (and is the real edge): load is stable
  over time, and hot experts deserve extra replicas. That's true for DS-R1 and
  Qwen3 alike — your algorithm just applies it to whatever load histogram it
  receives.

  One caveat worth repeating: we've only seen the LmSys sample for each model.
  The hidden Mix/ShareGPT/WildChat traces could be more volatile, which is
  exactly why a robust, data-driven (not hand-tuned-per-case) heuristic is the
  safe bet.

  So the answer to "can't we calculate it on the fly and adapt?" is: yes, that's
  precisely the intended design. Adapting to the observed load is the
  algorithm. You're still deterministic and still model-agnostic — you're just
  letting the measured statistics steer where the redundant slots go.

  Two levels of "adapting"

  There are actually two things you can adapt, both driven by stats you compute
  yourself:

  1. Spatial — where to put replicas. Compute per-layer skew → give the
  most-imbalanced layers (DS-R1 layer 21 in our EDA) more of the redundant
  slots, and barely touch the already-balanced ones. This is the high-value one.
  2. Temporal — when to redeploy. Compare load across sub-windows of hotness →
  if it's drifting, redeploy; if it's stable (which the EDA says it is, corr ≈
  0.98), return change=False and save the transfer cost.

  The one real limitation

  The only thing you genuinely don't have is the future and the other 
  layers'/iterations' ground truth — you only see a trailing window. So your
  adaptation is reactive: you assume the next stretch looks like the window you
  just saw. That assumption is safe here precisely because load is stable, but
  it's the one place where "adapt on the fly" can bite you if a hidden dataset
  turns out to be volatile.

  So: you don't get Gini as an input, but you don't need it as an input — you
  compute it, and adapting on it is exactly the move. Want me to draft a
  rebalance() that does this skew-driven slot allocation and benchmark it

❯ in the input whats the window.                                                

● The window is the trailing slice of recent iterations the simulator hands you
  — its length is the config value collection_interval.

  Where it comes from

  In dynamic_lb_simulator.py:168:

  train_window = self.expert_hotness[i - self.cfg.collection_interval : i]

  So when the simulator decides to call your rebalance() at iteration i, it
  passes the last collection_interval iterations of history, ending just before
  i. That slice is the hotness argument:

  hotness.shape == (collection_interval, n_layers, n_experts)

  It's the most recent batches only — never the future, never the whole trace.

  What the length actually is

  collection_interval is set per algorithm in run():

  - DS-EPLB → collection_interval = 1024 (dynamic_lb_simulator.py:220). So
  hotness is (1024, n_layers, n_experts).
  - Default → 0 (it never rebalances, so no window).
  - The base config default is 128, marked as the hyperparameter to tune for a
  proposed algorithm (dynamic_lb_simulator.py:352).

  So for the real algorithm slot, the window length is a knob you choose —
  that's exactly what the experiments/ds_eplb_sweep.py runs were sweeping.

  What one row of the window means

  Each row is one iteration ≈ one batch of traffic (~117k tokens for DS-R1,
  ~161k for Qwen3, ×8 routes). So a window of 1024 means "summarize the load
  over the last ~1024 batches, then decide a placement." Inside the DeepSeek
  adapter it's immediately collapsed to a single load vector
  (eplb_algorithms/__init__.py:29, weight = tokens_per_expert.sum(dim=0)) — the
  window is summed over time into per-expert totals.

  Why the size matters (the tradeoff)

  - Longer window → smoother, more stable load estimate (less noise), but slower
  to react if load shifts. Given our EDA showed load is very stable (rank corr
  0.98), a long window is basically free accuracy here.
  - Shorter window → reacts faster to drift, but noisier — you risk redeploying
  based on a transient spike, wasting transfer cost.

  There's also a second timing knob separate from the window: how often
  rebalance() is called. The next call only happens at i == redeploy_finish_iter
  + collection_interval + 1 (dynamic_lb_simulator.py:166) — i.e. after the
  previous redeployment fully finishes plus another collection_interval gap. So
  the same value controls both the window length and the minimum spacing between
  rebalances.

❯ and how often it pop or the rebalance can we change it too?                   

● Good — there are actually three separate timing mechanisms in the loop, and
  they're controllable to different degrees. Let me map them, because "how often
  it pops" and "how often it rebalances" are two different things.

  The three clocks in forward()

  1. How often rebalance() is called (the gap between cycles) —
  dynamic_lb_simulator.py:166:
  if i == redeploy_finish_iter + self.cfg.collection_interval + 1 and
  expert_ready:
  Controlled by collection_interval. Configurable (in the simulator) — but as I
  noted, it's fused with the window length. Change it the same way: config
  attribute or --intervals in the sweep.

  2. How often it "pops" (the drain rate) — dynamic_lb_simulator.py:154-158:
  if not expert_ready and i > algo_finish_iter and len(cur_layers_priority) > 0:
      adjust_layer_idx = cur_layers_priority.pop(0)   # exactly ONE layer
      self.transmit_amount_per_iter[i-1] += compute_redeploy_cost(...)
      cur_deploy_table[adjust_layer_idx] = next_deploy_table[adjust_layer_idx]
  This pops exactly one layer per iteration — it's hardcoded, not a config knob.
  The placement physically rolls out one layer at a time, charging that layer's
  transfer cost. To change the rate (e.g. 2 layers/iter), you'd have to edit 
  the simulator — there's no parameter for it in dynamic_lb_simulator.py.

  3. Algorithm compute time (a blocking delay) —
  dynamic_lb_simulator.py:177-178:
  algo_execute_iters = math.ceil((et - st) / 0.08)
  algo_finish_iter = i + algo_execute_iters - 1
  The wall-clock time your rebalance() takes is converted into simulated
  iterations during which nothing can be applied. A slow algorithm delays its
  own rollout. Not a knob — it's measured from your code. (Faster rebalance() =
  less delay.)

  What you can actually control, by role

  As a participant (submission.py) — you don't touch the drain rate or the gap
  directly, but you steer them through your return values:

  ┌──────────────────────┬──────────────────────────────────────────────────┐
  │      You return      │                 Effect on timing                 │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │                      │ Skip this cycle entirely — no pops, zero         │
  │ change=False         │ transfer cost. This is your main "how often"     │
  │                      │ lever.                                           │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ short                │ Fewer pops → redeployment finishes sooner →      │
  │ layers_priority (few │ redeploy_finish_iter comes earlier → next cycle  │
  │  layers)             │ sooner. Also less total transfer.                │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ order of             │ Which layers get fixed first (drained one per    │
  │ layers_priority      │ iter in this order). Put the worst-imbalance     │
  │                      │ layers first.                                    │
  └──────────────────────┴──────────────────────────────────────────────────┘

  So a participant effectively controls whether to rebalance, how many layers,
  and in what order — but not the 1-layer-per-iteration drain speed, and not the
  inter-cycle gap (that's collection_interval, the grader/simulator's).

  As the simulator owner (you, editing the repo): you can change all of it. The
  sweep script already adds a related knob — max_layers_per_cycle
  (ds_eplb_sweep.py:147-148) — which caps how many layers a cycle redeploys (it
  truncates the priority list):
  selected_layers = selected_layers[:max_layers_per_cycle]
  Note that caps the count per cycle, not the drain rate — it still pops one per
  iteration, just fewer total. If you want a true multi-layer-per-iteration
  drain, that's a simulator edit.

  Bottom line

  - Inter-cycle frequency → collection_interval: yes, configurable (coupled to
  window).
  - Pop/drain rate (1 layer/iter) → hardcoded; only changeable by editing the
  simulator.
  - Per-cycle layer count → not in the main sim, but the sweep script exposes
  --max-layers.
  - As a participant → you don't set these directly; you influence them via
  change, and the length/order of layers_priority.
